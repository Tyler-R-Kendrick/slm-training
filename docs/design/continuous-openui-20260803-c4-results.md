### `repair_harness` resolution: no code defect, documented decision

Traced the budget arithmetic in `scripts/run_autotrain_continuous.py` and
`src/slm_training/levers.py`:

- `MAX_RUN_MINUTES=3` (hard, non-negotiable repository cap) →
  `INTERRUPT_AFTER_SECONDS=170` → `MAX_HARNESS_WALL_SECONDS=155`
  (after `HARNESS_FINALIZATION_RESERVE_SECONDS=15`).
- `_arm_wall_minutes()` splits that symmetrically across the 2 required
  stages (train, eval) for a non-formal screening cycle:
  `(155 - 15) / 2 = 70s = 1.1667 min` — exactly the `campaign.json`
  `max_wall_minutes` observed for this campaign. The arithmetic is correct
  and working as designed; it is not a bug.
- This cycle's control recipe is generated by the "rotate recommended thrash
  arm" branch (`scripts/run_autotrain_continuous.py` around line 6488),
  which **always** pairs the rotating candidate hypothesis against a fixed
  `"both grammar levers off"` control (`compiler_decode_mode="off"`) —
  i.e. an **unconstrained-decode diagnostic arm**, by design, on every
  cycle that takes this branch (not specific to `component-plan`).
- Per the decode invariants (`AGENTS.md` §Non-negotiable architecture
  invariants; `docs/design/decode-invariants.md`), unconstrained decode is a
  diagnostic control only, never a default or gate input, and is expected to
  be slower — potentially much slower — than constrained decoding.
  `screening_decode_timeout_seconds` defaults to 24s **per record**; 3 smoke
  records at anywhere near that per-record cap alone approaches or exceeds
  the full 70s arm budget before Node/AgentV bridge startup is even counted.
- Conclusion: the repeated timeout on this specific control recipe is an
  **expected, structural consequence** of comparing against an unconstrained
  diagnostic baseline under the repository's hard 3-minute run cap — not a
  regression and not evidence of a defect in `bounded_process.py`,
  `run_autotrain_continuous.py`, or the AgentV bridge invocation.
- **No code change is made.** Widening `max_wall_minutes` or
  `decode_timeout_seconds` for this control specifically would either (a)
  weaken the non-negotiable `MAX_RUN_MINUTES` hard cap, or (b) risk masking
  genuine unconstrained-search blowups as fast passes elsewhere. Swapping to
  a faster control would test something other than what this control is
  for.
- **Successor approach** (not implemented in this cycle; a real design
  decision, not routine housekeeping): the "rotate recommended thrash arm"
  hypothesizer branch could reserve the `"both grammar levers off"` control
  for `promotion`-role campaigns (10–12 min stage budget, plenty of
  headroom) instead of `screening`-role continuous cycles (70s budget),
  or use a cheaper matched-control recipe for screening rotations. Filed
  here per decode-invariant I14 ("a rejected experiment closes an approach,
  never a goal") as the next thing to evaluate, not executed automatically.
